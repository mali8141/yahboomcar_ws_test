# Simulated Audio Field

This document covers the design and internals of the simulated audio pipeline
added to the digital twin. It does not duplicate the real-hardware UMA-16 docs
in `realworld_ws/custom_Sensors_ws/src/uma16/`, read those for the real
pipeline; this document is only about what was added for simulation and how to use it.

## Files added

| File | Purpose |
|---|---|
| `digitaltwin_ws/src/sim_audio/sim_audio/audio_field_builder.py` | CLI tool; used to generates a pre-baked audio field `.npz` file |
| `digitaltwin_ws/src/sim_audio/sim_audio/sim_audio_publisher.py` | ROS 2 node; loads the field at startup and publishes interpolated audio on `uma16/audio` at runtime |
| `digitaltwin_ws/src/sim_audio/package.xml` | ROS 2 package manifest |
| `digitaltwin_ws/src/sim_audio/setup.py` | Package entry points |

---

## Why this exists

Gazebo Harmonic has no acoustic physics engine. To still achieve a high fidelity audio enviroment without heavy computation a prebaked audio sampple field is generated and interpolated at runtime. This has some key advantages:

- **Decouples environment definition from runtime simulation.** The field
  can be generated by anything. As a proof of concept, a simple `sine_gradient` generator is included that produces a flat plane of sample points.
- **Deterministic and repeatable.** The same field file always produces the
  same audio at any given position, which matters for comparing mapping runs
  against each other.

Future audio filed builder might include more sophisticated generators, including ones that use external acoustic simulators to model propagation and reflections. The publisher and mapper do not need to know how the field was generated, they just interpolate the stored waveforms.

## The audio field format

The field is stored as two files:

```
<stem>.npz
<stem>_metadata.json
```

### NPZ arrays

| Array | Shape | dtype | Description |
|---|---|---|---|
| `points` | `[N, 3]` | float32 | World-frame `(x, y, z)` of each sample point |
| `waveforms` | `[N, chunk_size, 16]` | float32 | Per-channel time-domain audio at each point |

`N` is the total number of grid points. `chunk_size` must match
`uma16_audio_publisher`'s (and `sim_audio_publisher`'s) `chunk_size`
parameter (default 8192). The 16 in the last axis is the UMA-16 channel count.

### Metadata JSON

The sidecar stores everything needed to understand or reproduce the field:

```json
{
  "schema_version": 1,
  "generator": "sine_gradient",
  "coord_frame": "map",
  "bounds": { "x_min": -10.0, "x_max": 10.0, "y_min": -10.0, "y_max": 10.0, "height": 0.5 },
  "grid":   { "spacing": 0.5, "n_points": 1681, "n_x": 41, "n_y": 41 },
  "audio":  { "samplerate": 48000, "chunk_size": 8192, "channels": 16, "speed_of_sound": 343.0 },
  "sine_gradient": { "freq_min_hz": 200.0, "freq_max_hz": 2000.0, "amp_min": 0.1, "amp_max": 0.9, ... }
}
```

`schema_version` might be used for future testing of different field formats.

## The `audio_field_builder` tool

Generates the `.npz` + `_metadata.json` pair. Currently implements one generator: `sine_gradient`.

### `sine_gradient` generator

Assigns a pure sine wave to every grid point. Two properties vary
smoothly across the plane:

- **Frequency** varies linearly along the **X axis**: `freq_min` at `x_min`,
  `freq_max` at `x_max`. Default range: 200 Hz → 2000 Hz.
- **Amplitude** varies linearly along the **Y axis**: `amp_min` at `y_min`,
  `amp_max` at `y_max`. Default range: 0.1 → 0.9.

All 16 channels of each waveform are identical. Points are placed on a regular 2D grid at a fixed height (default 0.5 m) and ±10 m in both X and Y with each point spaced 0.5 m apart (41×41 grid, 1681 points). The generated waveforms are one chunk long (8192 samples at 48 kHz).

## The `sim_audio_publisher` node

### Startup

1. Loads `field_path` (`.npz`) into memory.
2. Validates that `chunk_size` and `channels` match the loaded field; if they
   differ, adopts the field's values and logs a warning.
3. Builds a KD-tree (`scipy.spatial.KDTree`) over the XY coordinates of all
   grid points for fast nearest-neighbour queries at runtime.
4. Sets up a TF `Buffer` + `TransformListener` to look up `map → base_footprint`.
5. Creates a publish timer at `samplerate / chunk_size` Hz (≈5.86 Hz for the
   defaults), matching the rate at which the real UMA-16 hardware fires its
   PortAudio callback.

### Per-tick interpolation

On every timer tick:

1. **TF lookup**: `lookup_transform(map_frame, base_frame, Time())`.
   If TF is temporarily unavailable (e.g. briefly during SLAM reinitialisation)
   the last known position is reused so audio keeps flowing.
2. **K-nearest search**: `KDTree.query(xy, k=4)` in the XY plane only.
   Z is ignored; the field is planar and the robot moves in XY.
3. **IDW blend**: weights are `w_i = 1/d_i²` (inverse-square, matching
   free-field acoustic 1/r² pressure-amplitude decay), normalised to sum to 1.
   The blended waveform is `Σ w_i × waveforms[i]` over the 4 nearest points.
   If the robot is exactly on a grid point (distance < 1 µm) the nearest
   waveform is returned directly to avoid division by zero.
4. **Publish**: wraps the `[chunk_size, 16]` array into a
   `std_msgs/Float32MultiArray` with the same `layout.dim` structure the
   real hardware publisher uses, and publishes on `uma16/audio`.

### Phase continuity

The publisher maintains a `_phase_offset` counter that advances by
`chunk_size` on every tick. On the next tick the waveform is `np.roll`'d by
`-offset` before publishing, so consecutive chunks are adjacent in the
looping waveform rather than always starting at sample 0. Because frequencies
are quantised to integer-period multiples, the roll is always a full-period
boundary — there is no click between chunks even as the robot moves and the
IDW weights change.

### TF frame convention

The publisher looks up `map → base_footprint` by default, matching
`audio_mapper_node`'s `map_frame` / `base_frame` defaults exactly. If your TF
tree uses `base_link` instead (common in the sim where the URDF root is
`base_link`), pass `-p base_frame:=base_link`.

## End-to-end pipeline

```
audio_field_builder (offline)
    writes audio_field.npz
            │
            ▼
sim_audio_publisher (ROS 2 node)
    loads .npz at startup
    polls /tf (map → base_footprint) each tick
    IDW interpolates 4 nearest field points
            │
            ▼ Float32MultiArray on uma16/audio
            │                                          ← identical wire format to real UMA-16
    ┌───────┴────────────────────────┐
    │                                │
    ▼                                ▼
audio_mapper_node              uma16_acoustic_overlay
(patrol_ws)           (custom_Sensors_ws)
    └──► audio_map.npz              └──► /beamforming_heatmap
    └──► view_audio_map.py
```

Everything below `uma16/audio` in the graph is reused unchanged from the
real-hardware pipeline.

## Current limitations

**No acoustic propagation.**: The current audio probe field generator is a simple flat plane with no obstacles or reflections.

**Uniform probe sequence length**: Currently every probe in the field has the same length. Future generators could produce variable-length probes to minimize file sizes while maintianing audio probe quality where it matters, but the publisher would need to be updated to handle that.

**Fixes sample spacing**: The current generator produces a uniform grid of sample points. Future generators could produce grid of sample probes with variable spacing / density to better capture the acoustic field in areas of interest, but the publisher would need to be updated to handle that.
